Five stages to the demo

The generator is done and measured. What does not exist is the service around it. This is the order to build it in, chosen so that every stage ends in something you could demo — because the demo may have to be given from whatever commit exists on the day.

01  Where things stand

One repo is real, the other is a scaffold

~/Dev/JumpAIS is the generator: 40+ commits, a 16-page golden set at zero collisions, a canary that must report exactly one, a browser-based checker and an animation probe. It works and it is measured.

~/Dev/jumpais-app is one commit: a compose file, an nginx config for the page origin, a vendored copy of the kit, and the plan this document replaces. No application code. 26 real generated pages sit in apps/pages/static/pages/ waiting to be served — that is what makes stage 1 possible without any backend at all.

Three things to do before stage 1, none of which take long.

Re-sync the vendored kit. packages/kit/VERSION pins ceec857 from 31 Aug. It predates every fix from the last two days — the canvas and 3D draw-in, the decrowding guard, the escaping rule, the checker's new columns. Copy the current kit over and re-stamp it.

Script that sync, do not do it by hand. The standalone demo bundle went stale twice in two days and shipped a model and a prompt the repo had already abandoned. It is now stamped with its commit so staleness is visible. The vendored kit needs the same treatment: one command that copies, hashes and stamps, and a check that fails loudly when the pin does not match what is on disk.

Leave the model and effort defaults alone for now. High beats medium on 3.8 across all 68 problems — 23 collisions against 35, half again as much animated geometry, more explanations. But 3.8 crowds more than 3.7 did at either level, and whether its denser pages are worth reading is a judgement call nobody has made yet. It changes a default, not a design. Decide it with real pages in the review screen you are about to build.

02  The build

Five stages, each one demoable

The order is dependency-driven, and it is also risk-driven: the parts most likely to misbehave in front of an audience come last, so that a bad week never leaves the demo broken. Nothing here is half-built at any point.

  1. 1

    Student view, on fixtures

    Serve the 26 existing pages from the page origin and embed one in a sandboxed iframe. Get the step-through, the sticky diagram and the mobile layout right. No API, no database, no model calls. This is where the product either feels good or does not, and it costs nothing to iterate on.

    DemoableA student stepping through a real solution, on a phone.

  2. 2

    Teacher console and review, still on fixtures

    Submit box, queue, and the review screen: the page on one side, the check report on the other, approve or reject. Fake the report from the JSON the checker already emits — it is the same shape you will get for real in stage 3.

    DemoableThe entire human loop, end to end, with no model in it.

  3. 3

    Database, worker, real generation

    Postgres, the schema below, one worker loop, SSE progress. This is where the 30–90 second wait becomes real, so it is also where the waiting screen has to earn its place — stream the checks as they land rather than showing a spinner.

    DemoableA teacher types a problem and watches a page get built and audited.

  4. 4

    Student chat, scoped to the page

    Context assembled from the approved page — each step, its why, the answer and its sanity check — never from a fresh solve. Answers cite step numbers.

    DemoableA student asking "why does step 3 work?" and getting an answer that points back at the page.

  5. 5

    Photo upload — direct multimodal generation

    Last on purpose. It is the stage most likely to misbehave on stage, and putting it last means it cannot destabilise anything else. The editable extracted-text field is not a nicety; it is the only mitigation that exists.

    Implemented as a single Gemini call. Image bytes are passed directly to kit/generate.py as a multimodal Part alongside the generation prompt. There is no separate extraction step — the model reads the problem image and emits the interactive HTML page in one pass. The model transcribes the Thai problem statement directly into Shell.page({ title, problem }), which the worker extracts into problem.extracted_text and displays alongside the draft card for teacher verification before publishing.

    The worker processes up to three jobs concurrently using ThreadPoolExecutor with FOR UPDATE SKIP LOCKED row-level locking so multiple workers or threads never race on the same job.

    DemoableA photo of a textbook problem becoming a solution page — in one model call, geometry intact.

02b  Implementation notes

Decisions made during build

KaTeX is bundled, not injected at runtime. The web app (apps/web) imports katex and katex/contrib/auto-render as npm packages (katex@^0.18.5). Math in problem titles, chat history entries, and nav bars is rendered by the <MathText> component which calls renderMathInElement on a DOM ref. The generated pages themselves (served from the pages origin on :8080) continue to load KaTeX from their own bundled lib/katex.min.js — these are two independent consumers.

Incremental lesson publishing. POST /lessons/{id}/publish now requires at least one approved problem, not all of them. Students see only the approved subset; problem_count in the lesson list reflects approved-only problems when published_only=true is requested. Rejecting or deleting a problem only reverts the lesson to draft if no other approved problems remain.

03  Data

The schema, and the one field that matters most

problem      id, source('text'|'image'), raw_text, image_path,
             extracted_text          -- editable; the only OCR mitigation
             extraction_confidence, level, created_by, created_at

page         id, problem_id, kit_version, model, effort,
             html_path, thumb_path, path_chosen('board'|'svg'),
             checks_json             -- window.__shellCheck, verbatim
             status('generating'|'ready'|'approved'|'rejected'), created_at

job          id, problem_id, kind('extract'|'generate'), state,
             stage, progress_json, attempts, error, started_at, finished_at

review       id, page_id, reviewer, action, note,
             seconds_on_page         -- see "rubber-stamping" below
             created_at

chat_message id, page_id, student_id, role, content, created_at

kit_version is not bookkeeping. It is what makes "improve the shell, re-execute every past page" possible, and that has now paid off repeatedly: the LaTeX-escape fix, the table crash, the mirrorpoint fix, and most recently a draw-in fix that took 5 of 6 3D pages from completely static to animated without regenerating anything. Store it, and keep the ability to re-run a page against a newer kit.

Page HTML is never served by the API. It is written to the shared volume and served by the pages origin, sandboxed with allow-scripts and without allow-same-origin. Generated pages run model-written JavaScript; that is the whole containment story.

04  Review

What the review screen has to show

The checker emits more than a pass/fail, and the review screen is the only place any of it reaches a human. Surface these, worst first, and link each one to the step it belongs to:

SignalWhat it meansWhy a teacher cares
collisionsoverlapping labels, per stepsomething is unreadable at that step
collapseda LaTeX command written with one backslashthe student sees hatA; no other check can see this
leakedLaTeX outside $…$raw commands rendered as text
failed / unknown / NaNboard geometry that did not buildthe diagram is missing part of itself
MISSING-whya step with no reason givenit shows the move but not the thinking
pre / zero-stepsfigure built before step 1stepping reveals nothing; it reads as static
moved / far / bandlabels the placer relocatedon a positional diagram, a moved label is a defect

Every one of these was green on a page that was visibly wrong

A geometry construction came out with its compass arcs clipped to fragments and a stray filled sector, and scored clean on collisions, animation density, LaTeX and board health. It was caught by a person looking at it. Design the review screen so that the fast path is looking at the page, with the numbers as annotation — not a checklist that can be cleared without ever seeing the diagram.

Rubber-stamping is the failure mode that hides

The review gate is the strongest correctness layer in the system and it fails silently: if approving twenty pages is slow, teachers click approve without reading and every metric stays green. Record seconds_on_page from the first day so the failure is at least visible.

05  Demo day

Assume the network hates you

Pre-generate, and be honest that you did

Have two or three approved pages already in the database before you present. Generate one live because watching the checks stream is genuinely the best part of the pitch — but never be in a position where a rate limit or a 40-second latency spike is the demo.

Do not read a single run as a quality score

Regenerating the same 68 problems twice moved the collision count on 5 pages, with gross movement larger than the net change. Model output varies run to run. If you show numbers, show them for a fixed set of pre-approved pages, not for whatever was generated that morning.

Check the bundle stamp before you travel

dist/jumpais-demo/VERSION now records the commit, the build time, whether the tree was dirty and the model default. It exists because a stale bundle shipped twice. Look at it.

06  Carried

Risks that do not go away

  • Extraction. A misread photo yields a flawless page solving the wrong problem, and every automated check passes it. Editable text is the entire mitigation — which is why the human step sits between extract and generate, and why stage 5 is last.
  • Grade-appropriate method. A page can be correct by a method the class has not been taught. Nothing verifies this. It is judgement, and it is the likely rejection reason.
  • Model arithmetic. No CAS. The model computes its own numbers. This is the largest correctness gap in the system and no amount of shell work touches it.
  • Ill-posed input. Missing or contradictory values are undefined behaviour.
  • Never call sympify() on model output. It evaluates its input as Python — remote code execution on the worker. spikes/spike/render.py does the unsafe thing and must not be copied.
